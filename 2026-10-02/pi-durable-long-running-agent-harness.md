## 摘要

- Pi Durable 是 Earendil 隨 Pi 1.0 一同推出的實驗性套件，目標是支援可長時間運作、具容錯能力，而且能在不同環境執行的代理應用。
- 它把模型對話、工具呼叫與壓縮等工作都建模為可檢查點化的任務；程序中斷後可以從儲存狀態恢復，避免整段工作付諸流水。
- 一個 harness 能同時管理多個對話；對話可從既有訊息分支，彼此並行執行，也能各自使用不同模型、工具和執行環境。
- 擴充套件可提供提示詞區段、工具、hook 與自訂任務；所有工作都納入同一套持久化與恢復機制。
- 代理與應用狀態可一起存進文件，並在原子提交中更新，降低對話紀錄與待辦、工單等外部狀態不一致的風險。
- Pi Durable 仍屬實驗性產品；它展示了持久化、多使用者控制與可變更代理框架的設計方向，但也增加了系統複雜度，仍需真實部署驗證。

今天，Earendil 與 Pi 社群推出了 Pi 1.0。這代表團隊相信，經過長時間的打磨、維護與積極開發，Pi 已成為穩固可靠的建構基礎。Pi 仍會持續演進；除了 Pi 1.0，團隊也推出一個名為 Pi Durable 的實驗性新套件，專為能長時間執行、具持久性且可調整的代理而打造，而且可在各種環境中運作。團隊邀請社群一起參與，讓它成為最好的持久型代理 harness。

Pi 程式助理原本的設計目標，是在使用者自己的遠端或本機機器上、終端機裡，由單一使用者操作。如果程序中斷，使用者查看發生什麼事，再叫它繼續即可。Pi 1.0 專注於做好這件事，而且不會改變這個方向。

Earendil 想用最適合每個人的形式，讓所有人都能運用這項技術。為此，需要一個可以在任何地方執行、能從不同介面接入、支援沒有預設上限的長對話、能承受內外部重大故障，並允許多位使用者共同引導同一代理的 harness。

Pi Durable 就是為此打造的 harness。它不會取代 Pi 程式助理，而是一個用來建構各式代理應用的框架，當然也包括程式助理。它不只與 Pi 程式助理共用 pi-ai 等程式碼，也延續 Pi 的設計原則：精簡、易於改造。

Pi Durable 也讓團隊可以在不影響 Pi 程式助理的情況下，探索這個領域的不同設計。當團隊在 Pi Durable 上建構代理應用所學到的經驗證明有價值時，也會回饋到 Pi 程式助理。

## 什麼是 harness？

每個人對 harness 都有自己的定義。團隊先前曾談過這個概念，這裡重新介紹 Pi Durable 所採用的定義。

Harness 是一套儲存機制，加上執行一個或多個大型語言模型對話所需的運作架構。它提供模型可呼叫的工具，以及工具執行時使用的環境。

對話是使用者與代理之間互動的紀錄。代理則由大型語言模型、模型設定（例如思考層級），以及它能呼叫的工具所組成。

工具在執行環境中工作；環境可以是使用者的筆電、遠端虛擬機器，或記憶體中的沙箱。每段對話各自取得哪些工具、使用哪個執行環境，都可以不同。

從呼叫模型到執行工具，harness 執行的每一項工作都稱為任務。

和 Pi 的其他部分一樣，Pi Durable 的設計也希望代理本身能理解整套系統。整份原始碼（不含測試）大約 15,000 行，以 GPT 計算約 150,000 個 token，以 Claude 計算約 250,000 個 token，這是最極端的情況。實際上，要在 Pi Durable 上開發，代理很少需要讀完全部程式碼；例如，儲存後端就有 3,000 行，通常可以略過。

以下逐步介紹 Pi Durable 的設計，以及背後的考量。

## 在任何地方長時間執行

團隊希望代理能長時間執行，並且能在各種地方運作。目前所說的「任何地方」，指的是任何支援 JavaScript runtime 的環境。

Pi Durable 的 harness 建立在儲存後端之上。套件附有記憶體、SQLite 與 JSONL 儲存方式，也提供相容性測試套件與基準測試，方便開發者驗證自製後端。SQLite 與 JSONL 的儲存程式碼不依賴 Node API，只要加上小型轉接層，就能在 Bun 或 Cloudflare Durable Object 中執行。儲存介面刻意保持精簡，因此也容易建構在鍵值資料庫或 PostgreSQL 等系統之上。同一時間由一個程序擁有儲存空間，其他用戶端則連接到該程序。

採用 SQLite 時，harness 只會把目前工作集留在記憶體：包括正在活動的對話紀錄、執行中的任務，以及尚待處理的提交。其他資料則留在磁碟，需要時才讀取。舊訊息會在超出模型上下文窗口之前先經過壓縮摘要，因此活動中的對話自然受上下文窗口限制。即使對話累積數萬則訊息，記憶體用量仍能維持在合理範圍。

需要存取檔案或 shell 的工具，會透過執行環境取得能力。Pi Durable 內建 Node 執行環境，讓工具可以存取本機檔案。和儲存層一樣，執行環境介面也很小，開發者可以自行提供遠端執行環境，讓 harness 在一台機器上執行，而工具在另一台機器上工作。環境工廠會依每段對話的工作目錄建立工具環境，所以不同對話可以在不同位置執行。

## 能從故障中恢復

團隊希望代理能持續運作；無論是筆電休眠、容器重新部署，或機器耗盡記憶體導致程序死亡，代理都能從中斷處接續。

Pi Durable 會將每一步工作記錄為任務，並在繼續前先儲存檢查點。若程序中斷，新程序打開相同儲存空間後，就能找到尚未完成的任務，從最後一個檢查點繼續。若模型請求在途中被截斷，系統會重新送出請求；已產生的部分回答會留在對話紀錄中，並標示為已中止。中斷的工具呼叫如果可以安全重跑，就會重跑；否則模型會收到中斷通知並決定下一步。

Pi Durable 沒有內建子代理功能，但用幾行程式碼就能建立，下方的問題分類工具便是範例。子代理在自己的對話中運作，因此同樣能在故障後接續；若可安全重跑的工具負責呼叫子代理，它也能找回原本的子代理並等待結果。佇列中的訊息會保留。每次提交都可帶有 requestId，確保只會處理一次：用戶端在故障後重試時，會取回原始提交的結果，而不是再提出一次請求。

以「修復不穩定的登入測試」為例，代理送出任務後，程序可能剛好在工具呼叫途中死亡。新程序重新打開同一份 SQLite 儲存空間並執行 resume 後，就能續接未完成工作；即使再次提交相同 requestId，也會取得同一筆工作，而不是重複建立請求。

## 同時執行多段對話

團隊希望同一個 harness 能同時管理許多段對話，而且彼此不會互相阻塞。

Pi Durable 能讓一個 harness 同時執行任意數量的對話，且每段對話都具有同樣的持久性保證。對話可以從頭開始，也可以從既有對話紀錄中的任意位置分支；新分支能讀取父對話在該時間點以前的歷史，不必複製整份紀錄。

可以把它想像成一個 Slack 頻道：代理在有人提及它時回覆。之後有人開啟討論串，頻道本身是一段對話，而討論串則是從該串回覆位置分出來的對話。兩者可以同時執行，不會互相卡住。

每段對話也都會保存自己的代理設定，包括模型、思考層級、啟用的擴充套件與工具、額外指示，以及執行環境中的工作目錄。主代理旁邊可以安排一個審查代理，使用較便宜的模型、唯讀工具與獨立的程式碼工作目錄。

## 擴充套件

團隊希望代理的所有能力都能插拔，而且每個插入的元件都能參與持久化。

Pi Durable 的擴充套件是由系統提示詞區段、工具、hook 與任務組成的一個具名套件。應用程式會把擴充套件安裝到 registry；每段對話再選擇自己要使用哪些擴充套件與工具，並且只儲存它們的名稱。

### 系統提示詞區段

每次呼叫模型前，Pi Durable 都會依照該對話所選擴充套件重建系統提示詞，因此提示詞內容改變後，下一次請求就會採用新內容。Pi Durable 會在變更發生的位置，把提示詞差異記錄到對話紀錄中；重新啟動或建立分支時，模型看到的內容因此能保持一致。若模型支援在對話中途變更系統提示詞與工具，系統只需送出差異，提示詞快取也能繼續使用。

例如，專案脈絡擴充套件可以從每段對話各自的執行環境載入 AGENTS.md 與 skills，並在背景更新；每次請求時再呈現最新內容。

### 工具

每次工具呼叫本身也會成為持久化任務，系統會先記下呼叫意圖，再執行工具。故障後，只有標示為安全的工具才會重跑；否則系統會將中斷狀況與已儲存輸出一併告訴模型，讓模型決定如何處理。每段對話也能配置自己的工具集合，例如讓 Slack 討論串可以搜尋資訊，但不能部署服務。

例如，搜尋 issue 的工具只讀取資料，因此可安全重跑；部署工具若在故障時中斷，則不會再次執行，而會把中斷狀態回報給模型。

工具可透過 harness API 提交紀錄與文件、啟動任務和對話，並與其他對話互動。這讓建立子代理只需少量程式碼：工具建立一段由自己擁有的對話，為它設定較小的模型與獨立指示，再等待回答。子代理和其他對話一樣能在故障後恢復、統計自己的成本，也能在介面上顯示為工具呼叫底下的工作項目。

工具也能被後續擴充套件覆蓋或包裝。例如，某個擴充套件提供的 bash 工具，可以取代先前定義的同名工具；另一個擴充套件也可以替目前勝出的 bash 工具加上計時功能。

### Hooks

Hook 讓擴充套件能介入任務執行，包括產生模型回答、呼叫工具或進行壓縮。它們可以在請求送往模型前改寫請求、阻擋或改寫工具呼叫、替換工具結果、要求執行持續進行，或自行寫入摘要。

Hook 可能會在故障後再次執行，因此需要做決策時，可以把結果存成 memo：一個與任務一起保存的小值，而且第一次寫入的內容會成為最終值。以部署審批為例，hook 可在部署工具執行前詢問 Slack 是否核准，並把結果記錄下來；程序重啟後便能沿用原本的決策，不必重複詢問。

多個擴充套件可以同時 hook 同一事件。Hook 會依照對話選用擴充套件的順序串接，並由各自定義的鏈式處理規則控制。beforeTool 會把改寫後的參數傳給後續 hook，第一個阻擋請求的 hook 會中止整條鏈；afterTool 則會逐一傳遞結果。onYield 遇到第一個要求繼續執行的 hook 時就會停止，而 afterResponse 這類觀察者則會全部執行。一般 hook 發生例外時會回報並繼續執行；但 beforeTool 發生例外時會阻擋工具呼叫。

### 任務

Harness 本身使用內建任務執行對話，包括每次模型請求、每次工具呼叫，以及每次壓縮。擴充套件也能加入自訂任務，並使用相同的執行機制：每個步驟之後都保存檢查點，計時器能跨越重新啟動繼續運作，任務也能等待其他任務。

文章用拆分信用卡付款作為範例：結帳時會同時向多張卡扣款；若其中一筆失敗，其他付款任務就會中止並退款。每筆付款都有冪等鍵，因此故障後重跑時不會重複扣款。所有付款都是結帳任務擁有的子任務，若結帳中止，它們會由底層開始逐步清理副作用。

任務與對話構成一棵擁有關係樹。中止任務會由下而上中止它所擁有的工作，讓每項工作先清理自己的副作用；任務也只有在其擁有的工作都完成後才會結束。子代理採用相同模式：由啟動它的工具呼叫擁有。

任務預設屬於前景工作，也就是目前對話的一部分；只有任務全部完成後，對話才會進入閒置狀態。比方說使用者按下 Esc 中止對話時，這些任務與它們擁有的工作也會一起中止。背景任務仍屬於該對話，但不算目前工作的一部分，因此對話可先進入閒置，而一般中止不會影響背景任務。這適合不應隨目前回合結束的子代理，或預定明天觸發的提醒。若直接中止背景任務本身，或以 background 模式中止對話，任務仍會停止。

## 壓縮

團隊希望長對話可以繼續進行，而不用停下來等摘要。

在 Pi Durable 中，壓縮本身也是一種任務，能在對話繼續執行時同步進行。當上下文快要用完，系統就會在背景摘要較早的訊息，並於下一個回合邊界放入摘要。只有當下一次請求不壓縮就會超出限制時，對話才會等待摘要。如果供應商仍以請求過長為由拒絕，harness 會壓縮後重試一次。使用者也可以隨時用自訂指示手動壓縮；舊訊息始終留在儲存空間中。

重設則會更進一步：系統開啟新的上下文，可以附上一份交接說明。工具也能透過交還控制權，要求代理以同樣方式自行接手。由於舊訊息並未刪除，另一個工具仍能搜尋交接之前的歷史。這些機制足以建構一種代理：它可以交接給新的自己，稍後再查閱過去的工作。

## 持久化的應用程式狀態

團隊希望建構在代理之上的應用程式狀態，也能和對話本身一樣持久。

Pi Durable 將待辦清單、計畫、工單或對話所使用的沙箱等應用狀態，儲存在文件中。這些文件是與對話紀錄一起保存的型別化 JSON，並在同一個原子提交中更新，因此狀態不會和產生它的對話紀錄互相矛盾。每份文件也會指定分支建立時的初始值：沿用父對話分支當下的值、採用父對話目前的值，或重新建立一份。

例如，待辦清單文件可設定為對話範圍、可回溯歷史，並要求分支取得父對話在分支點時的待辦內容。新增待辦時，工具在同一交易中更新文件；模型每次收到請求前，系統也能把待辦清單呈現給模型。介面則可訂閱文件狀態，將新值即時顯示給使用者。

## 可變更

團隊希望代理執行時，也能修改它的程式碼而不必停止代理。

Pi Durable 允許在對話執行期間更新 registry。若以相同名稱安裝新版本的擴充套件，就會一次取代舊版。已經執行中的工具呼叫會繼續使用啟動時所取得的程式碼；後續工具呼叫則會改用新程式碼。

## 多人共同操作

團隊希望多人與多種用戶端都能同時使用同一組對話：查看進度、中途加入並引導代理。

Pi Durable 把介面所需的一切資訊都當成已提交狀態，因此任意數量的用戶端都能連接到 harness 裡的任意對話。用戶端首先會取得目前檢視，包含對話紀錄、串流中的回答、執行中的工具與輸出、佇列訊息、代理設定及用量；之後只會收到變更。較晚加入或重新連線的用戶端會直接取得最新狀態。任何用戶端都能引導執行中的對話，或排入後續訊息。

遠端用戶端可以使用 thread.watch() 取得每次提交的精確操作紀錄，資料量足以透過 socket 傳送。若想沿用程式助理熟悉的事件格式，也能使用 watchEvents() 將提交轉成事件，代價是網路傳輸資料會增加。

## 試用方式

Pi Durable 已可試用，但目前仍屬實驗性產品，API 未來可能改變。開發者可以在 Pi 程式碼庫中查看 packages/durable，閱讀 README、超過三十個範例，或參考採用 Pi Durable 建立的小型程式助理與旅遊規劃代理，再開始開發。

旅遊規劃器約有 1,300 行 TypeScript，其中大部分是文字介面；它看起來像程式助理，只是因為重用了 Pi 程式助理的終端機介面元件。範例展示一個子代理如何平行執行三項搜尋，同時主代理仍可與使用者對話；程序中斷後，安全的搜尋只重跑尚未完成的部分，使用者也能切換至子代理並引導它。回到主代理後，仍可一邊詢問、壓縮或調整工作，等報告回來後再整理成計畫。

團隊表示，接下來幾週會分享更多 Pi Durable 的應用，以及用它打造的 Slack bot 或 GitHub 分類工具等小型代理產品。團隊會先在內部實際使用 Pi Durable，再逐步公開經驗與成果。

## 常見問題：為什麼又選 TypeScript？

因為 TypeScript 最容易用來快速建立原型。大家也都知道，要把所有東西移植到 Rust 甚至組合語言都很容易。團隊不排除未來這麼做，但目前會先專注於 TypeScript。

## 持久化代理的價值，在於故障模型與控制權

Pi Durable 最值得注意的，不只是把對話存進資料庫，而是嘗試把模型請求、工具副作用、子代理與應用狀態統一放進可恢復的任務模型。這讓「程序死掉後怎麼辦」成為框架本身要回答的問題，而不是每個應用各自補一堆脆弱的重試邏輯。

不過，持久化並不自動等於安全或正確。工具是否能安全重跑、支付或部署等副作用如何做到冪等、人工審批如何在恢復後維持一致，仍需要應用開發者仔細設計。文章提出了 replay 標記、檢查點與 hook 等機制，但產品仍是實驗性套件，實際可靠度還要由更多部署案例驗證。

另一個值得觀察的取捨是：Pi Durable 把多使用者共同引導、背景任務與動態替換擴充套件列為核心能力。這讓代理應用可以從單人終端程式，延伸成長時間運作的服務；同時也讓權限邊界、追蹤責任與版本相容變得更重要。對開發者而言，挑選 agent framework 時，除了看模型工具整合是否便利，也應確認失敗恢復、不可重複副作用、狀態同步與人類控制權是否有明確語意。
